1The problem messaging solves

Today every request is synchronous: the caller waits until all the work is done.

Postman ──POST /transactions──▶ API ──▶ handler ──▶ Postgres ──▶ 201 Created
                                  (caller waits for all of this)

Now imagine adding AI categorization inline, inside AddTransaction:

Postman ──▶ API ──▶ handler ──▶ Postgres ──▶ Groq (1–3 s, sometimes down, rate-limited) ──▶ 201
  • Slowness. Every save waits 1–3 seconds for an answer nobody needs right away.
  • Coupling to failures. If Groq is down, do you fail the save? That would be absurd, because the transaction is valid.
  • Rate limits. A 200-row CSV means 200 Groq calls in one request, and half of them fail on the free tier.
The fixSave the transaction now, and do the slow part later, somewhere else. "Later, somewhere else" needs something that remembers the pending work reliably, even if a process crashes. That's a message broker, and RabbitMQ is one.

The key property is decoupling. The sender doesn't know who reads the message, when, or whether that reader is even running. If the Worker is stopped, messages wait in the queue, stored on disk. Start the Worker an hour later and it works through everything that piled up.

Why an exchange instead of writing straight into a queue?

The publisher shouldn't know who's listening. The API publishes "a transaction was added" with the routing key transaction.added, and the exchange copies the message into every queue bound to that key. Later you might add a "check budget overspend" queue on the same key. The API code doesn't change; you only add a binding and a consumer.

Events vs commands

Event: a fact about the past

TransactionAdded. "This happened." The publisher doesn't care whether zero, one or five consumers react. Travels over RabbitMQ.

Command: an instruction

SuggestCategoryForTransactionCommand. Aimed at exactly one handler. Sent through MediatR inside the Worker, in response to the event.

3What happens when something crashes

The API calls are easy. What you're really learning with RabbitMQ is the failure cases.

Acknowledgements (acks)

When RabbitMQ gives a message to the Worker, it doesn't delete it. It marks it as delivered, unacknowledged and waits:

  • The Worker finishes the work and sends an ack. Only now is the message deleted.
  • The Worker crashes midway, so the connection drops without an ack. RabbitMQ redelivers the message.
Gotcha: when you ackAck first and do the work second, and a crash in between loses the message forever. So we ack only after the work succeeds. That's called manual ack (Piece 3).

Duplicates are normal: at-least-once delivery

Say the Worker saves the category, then crashes just before acking. RabbitMQ redelivers, so the same message is processed twice. No broker can guarantee "exactly once" across crashes.

The answer: idempotent consumersProcessing a message twice has the same effect as processing it once. The handler first checks "does this transaction already have a category?" If so, it does nothing and acks. That check also protects your manual categorizations from being overwritten by the AI.

Poison messages → dead-letter queue

Some messages fail every time, for example because the transaction was deleted or there's a bug. After N attempts we reject the message, and RabbitMQ moves it to a dead-letter queue (DLQ): a "failed mail" box you can inspect. It's out of the way, but not silently lost.

The dual-write problem → the transactional outbox

await _transactionRepository.AddAsync(transaction);                 // write #1: Postgres
await _publisher.PublishAsync(new TransactionAdded(transaction.Id)); // write #2: RabbitMQ

These are two systems with no shared transaction:

  • Postgres succeeds, then RabbitMQ fails (or the API crashes between the lines). The transaction is saved but never categorized. No error, no retry: a silent bug.
  • Publish first: now the Worker may receive an event for a transaction that was never saved.

The fix is the outbox:

  1. In the same DB commit as the transaction row, insert a row into OutboxMessages. Both rows exist, or neither does.
  2. A background outbox relay publishes unsent rows to RabbitMQ and marks them sent.
  3. If RabbitMQ is down, rows wait in Postgres and the relay retries later.

If the relay crashes after publishing but before marking a row sent, it publishes that row again, which is why consumers must be idempotent. These pieces lean on each other (Piece 4).

Eventual consistency

Right after POST /transactions, a GET may show the transaction as uncategorized; a second later it has a category. The data will become correct, just not instantly. That's fine for categorization. It's also why GetSpendingInsights stays synchronous.

4How it fits your Clean Architecture

Domain doesn't change at all, and most of the Application layer stays as it is.

                 ┌──────────────── Domain ────────────────┐
                 │  Transaction, Category, Categorizer…    │  unchanged
                 └──────────────────▲──────────────────────┘
                                    │
                 ┌───────────── Application ───────────────┐
                 │  existing handlers                       │
                 │  + ports: "record this event" (outbox),  │
                 │           ICategorySuggester (AI)        │
                 │  + new command: SuggestCategoryFor…      │
                 └────────▲───────────────────────▲─────────┘
                          │                       │
              ┌─── Infrastructure ────────────────┴───┐
              │ EF Core, repositories, Groq (existing) │
              │ + OutboxMessages table                 │
              │ + RabbitMQ publisher / consumer code   │
              └──────▲─────────────────────▲───────────┘
                     │                     │
            ┌────── API ──────┐   ┌───── Worker (NEW) ─────┐
            │ host #1          │   │ host #2                │
            │ HTTP → MediatR   │   │ message → MediatR      │
            └──────────────────┘   └────────────────────────┘
The idea to rememberThe Worker is a second entry point, like the API, into the same Application layer. A controller turns HTTP into a MediatR command; a consumer turns a message into a MediatR command. Both are thin adapters. The Worker has its own Program.cs calling AddApplication() and AddInfrastructure(), making it a second composition root.

Application never references RabbitMQ.Client, following the same rule as your repositories and IInsightsGenerator.

One transaction, end to end

  1. POST /api/transactions
  2. AddTransactionCommandHandler: no rule matches, so the category is null
  3. One Postgres commit: the Transactions row plus an OutboxMessages row {TransactionAdded}
  4. API returns 201 right away (uncategorized). The user is done waiting.
  5. asynchronous from here
  6. The outbox relay (in the Worker) publishes the row to the exchange and marks it sent
  7. The exchange routes transaction.added to the categorize-transaction queue
  8. The Worker consumer sends SuggestCategoryForTransactionCommand via MediatR
  9. Already categorized? Skip. Otherwise ask Groq to pick one of the existing categories
  10. Valid answer: save it. Nonsense answer: leave the transaction uncategorized
  11. Consumer acks, and RabbitMQ deletes the message

CSV import follows the same pattern one level up. The API stores an import job and returns 202 Accepted with a job ID ("accepted, not done yet"). The Worker performs the import, and you poll GET /api/imports/{id} for status and per-row errors.

1 · Service names are hostnames

Inside the network, the API reaches Postgres at Host=postgres, and the API and Worker will reach RabbitMQ at rabbitmq:5672.

The #1 beginner Docker bugInside a container, localhost means that container itself: not your PC, and not the other containers. localhost:5672 from inside the Worker container finds nothing.

2 · Published ports are only for you

"5672:5672" maps a port on your Windows machine to the container. Containers talk to each other over the private network regardless. We publish 15672 for the UI in your browser, and 5672 so a dotnet run Worker outside Docker can connect via localhost:5672. That's the one case where localhost is right.

3 · Volumes keep data across restarts

A container's own filesystem is thrown away when the container is recreated. rabbitmq-data:/var/lib/rabbitmq keeps durable queues and their waiting messages. docker compose down -v deletes volumes, and all that data with them.

Why hostname: rabbitmqRabbitMQ names its data folder after the container's hostname. Without a fixed one, every recreated container gets a random name, looks in a different folder, and starts empty. Your volume would be kept but never read.

6The management UI · http://localhost:15672

  • Overview: node status and message rates.
  • Exchanges: built-in amq.* ones exist already. Ours appears in Piece 3.
  • Queues and Streams: Ready means waiting for a consumer; Unacked means handed to a consumer with no ack yet. Stop the Worker, add transactions, and watch Ready grow. Start it and watch it drain. That's decoupling, visible. Click a queue and use Get messages to peek at the JSON.
  • Connections / Channels: whether the API and Worker are actually connected. A connection is one TCP connection per process, and it's expensive to open. A channel is a lightweight virtual connection inside it: IChannel in RabbitMQ.Client 7.x.

7Healthchecks: what and why

The problem: "the container is running" ≠ "the program inside is ready". The RabbitMQ container exists within a second, but RabbitMQ runs on Erlang (a separate runtime, a bit like .NET's CLR). It has to boot that runtime, load plugins, recover queues from disk, and only then open port 5672. That takes about 10–30 seconds. A Worker connecting at second 1 gets "connection refused" and crashes.

What a healthcheck is: a command Docker runs inside the container on a timer. Exit code 0 means healthy.

healthcheck:
  test: ["CMD", "rabbitmq-diagnostics", "-q", "check_port_connectivity"]
  interval: 10s   # run the check every 10 seconds
  timeout: 5s     # a check taking longer than this counts as a failure
  retries: 10     # this many failures in a row → "unhealthy"

The status moves from health: starting to healthy (or unhealthy), which you'll see in docker compose ps.

What it's for: the dependent service waits for it.

depends_on:
  rabbitmq:
    condition: service_healthy

Plain depends_on: [rabbitmq] only waits for the container to start, which doesn't help us. Your api → postgres dependency already does this properly with pg_isready, and the Worker gets the same treatment in Piece 2.

Why check_port_connectivity, not pingping asks "is RabbitMQ's runtime alive?", which can be true just before port 5672 opens. check_port_connectivity asks "can I actually open a TCP connection to every port RabbitMQ listens on?", which is what a client cares about.

Two limits, so you don't over-trust healthchecks

  1. They only protect startup ordering. If RabbitMQ restarts while the Worker is running, the Worker's own reconnect logic has to cope (Piece 3).
  2. Docker Compose does not restart an unhealthy container; it only reports it. Acting on health status is Kubernetes' job, which connects to your ADR 0009 (liveness vs readiness) in Phase 6.
